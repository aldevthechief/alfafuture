# API агентского цикла и фоновая обработка PDF

## Ленивая загрузка ленты

Фронтенд запрашивает `GET /v1/jobs?include_results=false`: только метаданные заданий без результатов.
Опрос одного задания поддерживает `GET /v1/jobs/{id}?include_result=false`.
`GET /v1/jobs/{id}/insights` возвращает краткие карточки: заголовок, первый вывод, роль, дату и счётчики блоков.
Источники, полные утверждения и исходный результат передаются только при открытии карточки через
`GET /v1/jobs/{id}/insights/{result_index}`. Индекс берётся из краткой карточки; ответ содержит исходный результат
в `result.results[0]` для прежнего адаптера и регистрации обсуждения. Все три маршрута соблюдают `X-User-ID`.
Прежняя полная выдача `/v1/jobs` и `/v1/jobs/{id}` остаётся доступна по умолчанию для других клиентов.
На главной монтируется только виджет одного инсайта; лента монтируется при переходе в сервис и показывает по 8 карточек.

## Запуск

Весь сервис из корня проекта: `docker compose up -d --build`.
Поднимаются Redis, основной API (http://localhost:18000), API диалога (http://localhost:18001) и фронт (http://localhost:5173).
Внешние порты API настраиваются через `BACKEND_PORT` и `FEEDBACK_PORT`; внутри контейнеров остаются 8000/8001.
CLI-контейнер `pipeline` находится в отдельном профиле `tools`; для работы веб-приложения он не запускается.

Из корня проекта в виртуальном окружении Python 3.12:

```powershell
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe -m uvicorn backend.app:app --host 127.0.0.1 --port 8000
```

Swagger: http://127.0.0.1:8000/docs
OpenAPI JSON: http://127.0.0.1:8000/openapi.json
ReDoc: http://127.0.0.1:8000/redoc

Запускайте один процесс Uvicorn: очереди и публикация версий синхронизированы внутри процесса. Параллельность обеспечивают отдельные пулы: 4 анализа и 2 отчёта. Оба имеют ограниченную очередь; /v1/analyses возвращает 429 при её заполнении. Пакетные методы возвращают принятые jobs и оставшиеся items/files явно. Несколько HTTP-запросов не блокируют работающие агенты.

LLM_API_KEY и остальные параметры моделей берутся из существующего common/llm/.env/окружения. Модели, Tesseract и зависимости должны быть доступны для соответствующих стадий. Swagger и /health не требуют ключа. Фоновый импорт существующих отчётов может загрузить E5 при отсутствии локальных весов; без обязательных зависимостей задание завершается с явной ошибкой до платных вызовов OCR. На старте исходные PDF импортируются фоновыми заданиями с переиспользованием их кешей. Их готовность видна через /v1/jobs и /v1/reports; ранний анализ использует уже готовые материалы.

### Платёжная аналитика

`GET /v1/companies/U_14366/payments?direction=out&sort=amount&offset=0&limit=15` принимает
`direction=in|out`, `sort=amount|count`, поиск `q` по компании, номеру, отрасли и региону,
`offset >= 0` и `limit=1..100`. Используется тот же `X-User-ID`, что и в остальных запросах кабинета.
Ответ содержит `summary` и `flows` для обоих направлений, страницу `counterparties`, её `total`,
отдельные `self_transfers` и замечания о качестве исходных данных в `data_notes`.
Поиск и пагинация не меняют итоговые суммы и знаменатель долей.

Источник — очищенные общим `common.data.load()` таблицы компаний и агрегированных платежей CSV.
Количество платежей — сумма `PAY_CNT`, средний платёж — сумма `PAY_AMT` / сумма `PAY_CNT`.
Переводы между своими счетами исключены из входящих и исходящих потоков. Контрагенты без отрасли
или региона включены в общую сумму и отдельные категории «неизвестно». Дат отдельных операций
в CSV нет: `period=null`, календарная динамика не рассчитывается.

LLM не используется. Таблицы и индексы связей загружаются один раз при первом запросе в процессе,
результаты компаний кешируются в памяти. После замены CSV нужно перезапустить API.
Отсутствующие таблицы дают 503, неизвестная компания — 404; метод доступен и в режиме `server`.

### Контрагенты

`GET /v1/companies/{id}/counterparties` принимает `direction=all|in|out|both`, `group=all|own`,
`sort=amount|in|out|count|name`, поиск `q` (до 120 символов), `offset` и `limit` с теми же границами.
`in` и `out` включают двусторонние связи; `both` оставляет только их. `amount` сортирует по сумме
поступлений и списаний. В `items` каждая компания представлена один раз: `in` и `out` содержат
сумму, количество, средний платёж и долю в соответствующем потоке владельца кабинета.
`summary` считает уникальные компании, входящие, исходящие, двусторонние связи и свою группу
до применения фильтров. При неизвестной группе `group_known=false`, `same_group=false`:
это не подтверждение принадлежности к другой группе.

Карточка `/counterparties/{counterparty_id}` возвращает `counterparty`, `profile` (город,
группа, выручка, градации возраста и численности) и `data_notes`. Компания, отсутствующая
в справочнике, сохраняется в платёжном списке; её `profile.available=false`.
Несвязанный с владельцем контрагент даёт 404, даже если он присутствует в справочнике.
Все расчёты используют тот же экземпляр `PaymentAnalytics`, таблицы, индексы и кеш;
новых обращений к агентам нет. Переводы себе и данные о датах учитываются так же, как в аналитике.

### Раздел «Компания»

Использует существующий `GET /v1/companies/{id}`. Прежние `card`, `facts` и поля `profile`
сохранены; в `profile.overview` добавлены выручка компании и группы, размер группы и масштаб компании,
ОКВЭД, данные ФТС, исходные факты о персонале, развитии, собственности, географии и группе,
а также замечания о качестве данных. Факты сохраняют источник и исключают гипотезы.
Профиль загружается один раз существующим загрузчиком; дополнительных агентов и чтения CSV
для новой проекции нет. Численность остаётся градацией, направление внешнеторговых операций
не выдумывается, страны сохраняются и при противоречащем им флаге ФТС.

Пример POST /v1/analyses:

```json
{
  "company_id": "U_68622",
  "role": "cfo",
  "engine": "judge",
  "source": "both",
  "retrieval": "v2",
  "candidates": 30,
  "judge": 5,
  "workers": 4,
  "analytics_cache_only": false,
  "analytics_share": 0.4
}
```

В Swagger описаны все флаги pipeline.py: company_id, role, candidates, judge, workers, engine, retrieval, source,
analytics_cache_only, analytics_refresh, analytics_share, ocr, bank_charts, bank_tables, bank_digest, bank_prepare,
ocr_budget, charts_budget, tables_budget, digest_budget.
Единственный публичный движок — `judge` (можно не передавать `engine`). `engine=loop` отклоняется с 422;
устаревшие поля `bank_review`, `bank_insights`, `bank_budget` удалены из схемы и также отклоняются.
OCR, графики, таблицы и выжимки готовятся до запуска графа judge; его поиск получает новую опубликованную версию.
Неверные сочетания и нечисловые бюджеты отклоняются с 422; бюджет требует включённой стадии.

Для /v1/analyses/batch отправьте {"items": [<AnalysisRequest>, <AnalysisRequest>]}.
Каждый запрос получает собственные результаты, журналы и каталог HTML-карточек. Ошибка одного задания не отменяет другие.

Для персонализированного подбора передайте `X-User-ID: demo-user` в `POST /v1/analyses` или
`/v1/analyses/batch` (альтернатива — поле `user_id` в AnalysisRequest). При наличии обоих они должны совпадать.
Используется та же SQLite `data/feedback/feedback.sqlite3`, что и у `feedback_api`, по паре компании и роли.
В новостном графе «уже знаю»/«не интересно» исключают новости до оценки; лайки/дизлайки меняют приоритет,
а уточнения идут отдельным блоком непроверенного пользовательского контекста. Банковская ветка analytics
остаётся общей. Идентификатор является соглашением локального прототипа, а не банковской аутентификацией.
При чтении `/v1/jobs` и `/v1/jobs/{id}` передавайте тот же `X-User-ID`: чужие персональные задания не выдаются,
без заголовка видны только общие задания. Без пользователя анализ работает в прежнем общем режиме.
Результаты news judge сохраняют `evidence_facts` с исходной нумерацией writer; импорт в `feedback_api`
использует эти строки и расчётные факты, а не актуальную на момент обсуждения таблицу компании.
Новые результаты также содержат `evidence`: снимок новостей, фактов и банковских фрагментов, переданных writer.
Фронт отправляет исходный результат в `POST /v1/insights/import` сервиса диалога (порт 8001)
с `registration_key=<job_id>:<insight_id>`. Повторная регистрация тем же пользователем возвращает прежний ID
и сохраняет историю; другое содержимое инсайта с тем же ключом даёт 409. Методы вопросов, реакций и истории
описаны в [feedback_api/README.md](../feedback_api/README.md). Во всех запросах используется тот же `X-User-ID`.
При `ALFA_CACHE_REDIS_URL` сервис диалога кеширует проверенные ответы в Redis с учётом пользователя,
контекста, источников и модели. `FEEDBACK_LLM_CACHE_TTL=3600` — срок в секундах, `0` отключает кеш.
Смена контекста или результатов повторных поисков требует нового вызова модели; история остаётся в SQLite.
Старые результаты без снимка используют сохранённые факты и проверку версии корпуса; если исходные новости
недоступны, нужен новый анализ.

CLI: `python -X utf8 pipeline.py U_68622 --role cfo --source news --user-id demo-user`.
Пользовательские CLI-результаты получают суффикс хеша user_id и не перезаписывают общую выдачу.

При source=both новостной judge и банковский агент работают параллельно. workers задаёт параллельность обработки новостей.
Подготовка PDF завершается до фиксации версии банковского поиска; при ошибке подготовки judge не запускается.
Задание закрепляет снимки новостей и банковской аналитики до завершения. Legacy run_loop() и его модули сохранены в исходниках,
но HTTP-бэкенд и CLI их больше не вызывают.

## Чат с банком

В `feedback_api` доступен отдельный разговор о компании:
`POST /v1/company-chats` с `{company_id, role}`, `GET /v1/company-chats/{id}/messages`
и `POST /v1/company-chats/{id}/ask/stream` с `{question, request_id, selected_text?}`.
Все запросы используют `X-User-ID`; разговор изолирован по пользователю, компании и роли.
`GET` возвращает последние 50 сообщений и курсор `before` для предыдущих, без запуска модели.
SSE-протокол и проверка источников общие с обсуждением инсайта, контекст и история отдельные.
Снимок профиля сохраняется для каждого вопроса; точный повтор запроса сохраняет прежний снимок.
Ответы содержат проекцию `evidence` с процитированными фактами и `analysis.retrieved_sources`
с найденными материалами (включая название, URL, страницу и дату, когда они известны).
Переписка не создаёт записей реакций и не меняет персонализацию автоматически.
Полный контракт: [feedback_api/README.md](../feedback_api/README.md#отдельный-чат-компании).

## Профиль компании и уточнения

Профиль интерфейса берётся из `GET /v1/companies/{id}` основного API. В `feedback_api` (порт 18001,
на фронтенде префикс `/feedback`) доступны следующие методы с тем же `X-User-ID`:

| Метод | Назначение |
|---|---|
| GET /v1/companies/{id}/questions?role=cfo | Вопросы по предположениям текущей ленты и ранее сохранённые ответы |
| PUT /v1/companies/{id}/answers/{question_id} | Сохранить или изменить ответ |
| DELETE /v1/companies/{id}/answers/{question_id} | Удалить уточнение |
| GET /v1/companies/{id}/personalization?role=cfo | Контекст следующего анализа, включая `answers` |

Тело PUT: `{"statement":"Портфель компании смещён в автотранспорт", "verdict":"yes", "text":""}`.
`verdict` принимает `yes`, `no`, `other`; при `other` обязателен непустой `text` (до 500 символов).
`question_id` берётся из GET questions. Пропуск вопроса хранится только в текущем интерфейсе.
Вопросы выделяются правилами без LLM из гипотез и условий инсайтов той же объединённой ленты,
что видит пользователь: готовые кабинеты, общие и собственные задания. Чужие задания исключены.

Ответы хранятся в SQLite по пользователю и компании, доступны между ролями и после перезапуска.
В следующем новостном анализе они дополняют факты пометкой «со слов пользователя», а также передаются
как непроверенный пользовательский контекст. Исходные банковские факты не меняются; готовые инсайты
не пересчитываются при сохранении ответа. Банковская ветка `analytics` остаётся общей.
В режиме `server` профиль и ответы доступны для чтения; PUT/DELETE возвращают 403.

## Загрузка и кеш PDF

Откройте POST /v1/reports/upload в Swagger, выберите files и передайте options:

```json
{"ocr": true, "charts": true, "chart_mode": "selective", "tables": true, "digests": true, "ocr_budget": 15, "charts_budget": 8, "tables_budget": 7, "digest_budget": 3}
```

Бюджеты API задаются на один отчёт. По умолчанию все стадии включены. Для обработки только текстового слоя/готовых кешей
задайте все четыре флага false. Максимум 32 файла за запрос и 50 MiB на файл; проверяется структура PDF, зашифрованные/пустые файлы отклоняются.
После ответа 202 опрашивайте GET /v1/jobs/{id}. Список принятых jobs всегда возвращается отдельно от непринятых файлов при заполненной очереди.

`chart_mode` доступен в `/v1/reports/prepare`, опциях `/v1/reports/upload` и `/v1/analyses` при включённой
подготовке или `ocr`: `all` сохраняет все графики, `selective` выбирает добавляющие новую информацию,
`off` исключает графики. Флаг `charts`/`bank_charts` по-прежнему включает отдельную стадию распознавания;
`chart_mode` также управляет графиками в библиотеке фрагментов и Markdown для выжимок.
Явное значение важнее `BANK_CHARTS`; если оба отсутствуют, используется `all`.
Разрешённое значение фиксируется в параметрах подготовки и входит в ключ кеша отчёта:
`all`, `selective` и `off` получают разные версии. Готовые версии без этого поля читаются как `all`.
Изменение режима требует нового задания подготовки; уже опубликованные версии сами не переключаются.

CLI: `python -X utf8 pipeline.py U_68622 --engine judge --bank-charts --chart-mode selective`.
`--chart-mode` применяется с `--ocr`, `--bank-charts`, `--bank-tables`, `--bank-digest` или `--bank-prepare`.

У каждого отчёта отдельный каталог, определяемый именем, SHA-256 PDF, опциями подготовки и моделями.
OCR, таблицы, графики, фрагменты, выжимка и векторы кешируются там. Повторный запуск сохраняет оплаченные результаты.
Отчёты готовятся параллельно; одинаковая версия одного отчёта защищена отдельной блокировкой.
Неполная/ошибочная подготовка оставляет прежнюю опубликованную версию; её артефакты остаются для повторной попытки.

После полной подготовки, включая поисковый индекс и эмбеддинги, сервер атомарно обновляет current.json.
Новый отчёт доступен новым заданиям сразу после этого. Уже работающие задания продолжают с прежними объектами индекса и библиотеки,
не прерываются и не получают смену источников посреди вывода. Новый запуск получает обновлённый набор автоматически.
Если старое задание подготовки завершится после более нового для того же имени PDF, оно не заменит более новую запрошенную версию.

Данные API находятся в data/api/ (исключены из Git): jobs, загрузки, версии отчётов, результаты, кеш аналитического агента.
Статусы и результаты сохраняются на диск. После перезапуска queued/running получают interrupted: повторите запрос,
готовые артефакты PDF будут использованы повторно. Сервис не возобновляет оборванные LLM-циклы автоматически.

## Проверка

```powershell
.\.venv\Scripts\python.exe -X utf8 -m unittest test_backend_api
```

Тесты используют синтетические PDF и подменённые модели: проверяют OpenAPI, загрузку/статусы, реальную параллельность потоков,
независимость пулов, переиспользование отчётов, публикацию версий и сохранение старого снимка у работающего агента.
Нейросетевое качество и реальные затраты OCR этими тестами не измеряются.


## Подключение фронта и CORS

Готовые кабинеты: `GET /v1/cabinet/accounts` и общая лента
`GET /v1/cabinet/feed?company_id=…&role=…`. Короткий текст для экрана загружается отдельно
через `GET /v1/jobs/{id}/compact`: словарь по ID инсайта, значение — сокращённая версия или `null`.
Поддерживаются сохранённые задания `demo-…`; в режиме `server` читается только готовый кеш.
Полный текст и источники остаются в `/v1/jobs/{id}/insights/{index}`.

Фронт регистрирует открытый инсайт в `feedback_api` и отправляет вопросы в
`POST /v1/insights/{record_uuid}/ask/stream` с тем же телом, что `/ask`.
Ответ — SSE: `text` → `{"text":"текущий текст"}`, `complete` → сохранённый `FeedbackRecord`,
`error` → `{"status":502,"message":"…"}`. До `complete` текст предварительный;
финальный ответ проходит существующую проверку источников и сохраняется в SQLite.
Повтор того же `request_id` возвращает сохранённый ответ. В Docker путь начинается с `/feedback/`,
а прокси отключает буферизацию. JSON endpoint `/ask` продолжает работать.

Вопрос может содержать необязательный `selected_text` (до 2000 символов) — выделенный пользователем
фрагмент краткого или полного текста инсайта либо готового ответа агента. Поле `selected_source` различает
`insight` (по умолчанию) и `answer`. Фрагмент передаётся модели отдельно от вопроса, сохраняется
в `FeedbackRecord` и учитывается в последующих сообщениях и ключе кеша. Цитата обозначается как
читательский контекст, а не новый источник фактов. Прежний ответ агента требуется перепроверить по материалам.
При повторе `request_id` цитата и её происхождение тоже должны совпадать.
SQLite автоматически получает колонки `selected_text` и `selected_source` при запуске, прежняя история сохраняется.
Для вопросов без цитаты прежние промпты и ключи кеша остаются прежними.

Базовый URL локального API после запуска: `http://127.0.0.1:8000`.
Создание анализа: `POST /v1/analyses`, JSON — AnalysisRequest. Из ответа взять id,
статус и результат получать через `GET /v1/jobs/{id}`. Swagger: `http://127.0.0.1:8000/docs`.

Разрешённые origins по умолчанию: `http://localhost:5173`, `http://127.0.0.1:5173`,
`http://localhost:3000`, `http://127.0.0.1:3000`. Поддерживаются preflight OPTIONS,
GET/POST и заголовки Content-Type/Authorization. Для своего адреса фронта перед запуском:

```powershell
$env:API_CORS_ORIGINS="http://localhost:5173,https://frontend.example.com"
.\.venv\Scripts\python.exe -m uvicorn backend.app:app --host 127.0.0.1 --port 8000
```

При source=both ошибка банковского агента даёт `job.status=partial`, непустой `job.error`,
а новостные результаты сохраняются в `job.result.results`. В result.components указан отдельный
статус news и analytics, в result.errors — компонент и сообщение. Это относится и к исключениям,
и к ошибке в поле error завершившегося банковского run. При source=analytics такая ошибка даёт failed.
Отсутствие готового кеша при analytics_cache_only отмечается как cache_miss, без ложной ошибки выполнения.
Фронту следует показывать частичный результат вместе с ошибкой, а не считать partial полным успехом.

BankView ранжирует все опубликованные фрагменты совместно: общая BM25-выдача и ранги dense similarity,
один запрос к E5. При этом векторы документов продолжают храниться в отдельных кешах PDF. Контекстные окна
строятся после глобального отбора; материалы разных отчётов не склеиваются в одно окно.
Legacy HTML-карточки и трассировка loop сохранены для прямого вызова модулей, но CLI/API этот движок не запускают.
Векторный кеш retrieval v2 использует уникальные временные файлы, блокировку чтения/записи на модель
и объединение новых ключей перед атомарной публикацией; одновременные пополнения не теряют друг друга.


Если фронт работает на другом компьютере, запускайте Uvicorn с `--host 0.0.0.0`,
а фронту передайте `http://<IP компьютера с API>:8000`. `0.0.0.0` — адрес прослушивания,
его нельзя использовать как URL API в браузере. В API_CORS_ORIGINS укажите фактический origin фронта.

## Выгрузки сохранённых данных

Выгрузки не запускают анализ, подготовку PDF или LLM. Доступны в `full` и `server`.
Кнопки находятся в разделах «Инсайты», «Платёжная аналитика» и «Контрагенты».

| Запрос | Данные |
|---|---|
| `GET /v1/exports/insights?company_id=U_14366&role=cfo&format=xlsx` | Вся сохранённая лента выбранной компании и роли, объединённая так же, как `/v1/cabinet/feed` |
| `GET /v1/exports/insights?job_id=<id>&format=json` | Готовые инсайты одного доступного пользователю задания, в том числе `demo-<company>-<role>` |
| `GET /v1/exports/payments?company_id=U_14366&format=csv` | Суммы и число платежей по контрагентам в обе стороны; переводы между своими счетами отдельно |
| `GET /v1/exports/counterparties?company_id=U_14366&top=200&format=xlsx` | Топ поставщиков и покупателей по каждой стороне, концентрация и группа компании |

Форматы: `xlsx`, `csv`, `json`, `jsonl`. XLSX содержит отдельные листы; CSV для нескольких
таблиц возвращается ZIP-архивом с `meta.json`. Параметр `table` у инсайтов и контрагентов позволяет
получить одну таблицу. CSV: UTF-8 с BOM, разделитель `;`, десятичная запятая (`decimal=dot` меняет её на точку).
Строки из новостей сохраняются текстом, без исполнения формул в Excel.

У инсайтов доступны `origin=all|news|bank`, `date_from`, `date_to` (YYYY-MM-DD). Если передан
`job_id`, указанные дополнительно `company_id` и `role` должны совпадать с заданием.
В выгрузке сохраняются слои утверждений, источники, действия, версия аналитики и оговорки;
цитаты отчётов сокращены до 300 символов. Полные PDF, OCR и внутренние фрагменты не выгружаются.
Период платежей в исходных таблицах не указан — выгрузка его не восстанавливает.

Текущие фильтры интерфейса и локальное скрытие карточек не ограничивают выгрузку; это указано рядом с кнопками.
`scope=group` для платежей/контрагентов выгружает компании группы. Если используется
`data/api/access.json` (`user_id: [company_id или GROUP_ID, ...]`), доступ проверяется для каждой компании.
Необязательный `STAFF_API_TOKEN` даёт обход этого списка через серверный Bearer-токен;
в браузер он не передаётся. Отсутствие токена не включает такой обход. Владение приватным
заданием анализа или выгрузки всегда проверяется по текущему контракту `X-User-ID`.
Как и в остальных API проекта, этот заголовок — идентификатор для демо, а не полноценная аутентификация.

`POST /v1/exports` принимает `{items: [ExportQuery, ...], format: "xlsx"}` (до 50 пунктов)
и возвращает фоновое задание. `GET /v1/exports/<id>` — статус, `GET /v1/exports/<id>/file` — файл
после `succeeded`; до готовности файла возвращается 409. Очередь выгрузок отдельная от анализа и PDF.


## Живые стадии и готовые карточки

`GET /v1/jobs/{job_id}/events` отдаёт SSE-события `job`: метаданные задачи, `revision`,
`stage` и `feed` с проверенными превью. Заголовок `X-User-ID` обязателен для личной задачи;
чужая задача возвращает 404. Полные доказательства и `partial_results` в события не попадают.
Первое событие каждого подключения — текущий снимок, поэтому переподключение восстанавливает все готовые карточки.
Поток завершается на `succeeded`, `partial`, `failed` или `interrupted`; до этого приходят heartbeat-комментарии.

`stage` содержит `code`, `label`, `step`, `steps`, счётчики `done`/`total`, состояние параллельных веток и историю.
Коды идут вперёд: `queued` → `preparing_reports` (если нужна подготовка PDF) → `collecting` →
`analyzing` → `generating` → `verifying` → `finalizing` → `done`. Ошибка/перезапуск дают `failed`/`interrupted`.
Для анализа только банковских материалов план короче; фронтенд показывает серверный `label` и фактический план.

Новостные карточки публикуются после текущего объединения дублей, writer/checker и аудита.
Банковские карточки добавляются после действующей сверки с новостями и ограничения их доли.
Общая лента `/v1/cabinet/feed` сохраняет старые анализы и включает готовые карточки работающих,
ошибочных и прерванных задач. При сбое готовые строки остаются на диске.
Открывайте карточку через `/v1/jobs/{id}/insights/{index}?insight_id={stable_id}`: индекс может меняться.

Фронтенд читает SSE через fetch с заголовком пользователя. При обрыве/зависании потока он опрашивает
метаданные задачи и общую ленту, затем переподключается. Общая лента дополнительно обновляется раз в 5 секунд.
`revision` защищает от отката к устаревшему ответу опроса. Смена компании/роли отменяет прежнее подключение.
Новые карточки увеличивают существующий счётчик уведомлений и показывают уведомление с переходом к инсайту;
первоначально загруженная лента и повторный снимок не создают повторных всплывающих уведомлений.
