## Что уже входит в PR

1. **Сквозной LangGraph-пайплайн.** Новостной judge и агент аналитики Банка выполняются параллельно. Новостная ветка распределяет кандидатов на оценку и глубокую проверку; затем результаты объединяются с ограничением доли банковских карточек, приводятся к контракту Insight v2 и сохраняются. Ошибка одной новости обрабатывается отдельно от всей пачки.

2. **Поиск и контекст компании.** Включены профиль компании, факты из таблиц кейса, retrieval v2 по умолчанию, альтернативные v3 / hybrid / lexical и подбор под роль. Плотный поиск связанных новостей переведён с FRIDA на E5. Старый генератор банковских тезисов удалён; отдельные банковские инсайты выпускает агент аналитики.

3. **Аналитика Банка и подготовка PDF.** Есть OCR, извлечение таблиц и графиков, выжимки, поиск по материалам отчётов и проверяемые ссылки на источники. HTTP-сервис поддерживает загрузку PDF, фоновую подготовку, кеширование и публикацию версий. Работающий анализ использует закреплённую версию материалов.

4. **Формирование и проверка карточек.** Writer получает факты компании, банковские материалы и результаты расчётов. В карточке разделены факты, выводы AI, гипотезы и позиция Банка. Есть review и финальный аудит; отклонённые результаты остаются черновиками и не должны попадать в ленту как готовые инсайты. У judge есть инструмент расчётов на Python с формулами, источниками и допущениями.

5. **API и веб-интерфейс.** FastAPI создаёт одиночные и пакетные задания, отдаёт статусы, результаты, ошибки и поиск. Фронтенд показывает ленту, фильтры, карточку с источниками и профиль; позволяет выбрать компанию и роль и запустить анализ. Вопрос по событию отправляется в `/v1/insights/ask`, ответ поступает потоком. При недоступном API или отсутствии анализа показываются демонстрационные данные.

6. **Кеш и запуск.** Redis объединяет LLM-кеш и именованные кеши; volume сохраняет его между перезапусками. В Git включён сжатый LLM-кеш примерно на 5,7 МБ, есть скрипт прогрева. Compose поднимает Redis, backend и frontend; контейнеры анализа работают на CPU. В PR также организованы модульные, интеграционные и smoke-проверки.

В самом PR доступны оба движка — `judge` и `loop`. В более новой ветке `integration-demo` CLI/API уже переведены только на `judge`.

## Ограничения и следующие действия

- **Определить состав финального слияния.** Если команде нужны обсуждение, персонализация и выборочные графики, текущий PR #25 их не доставляет: нужно включить изменения из `integration-demo` и повторить проверки итогового коммита.
- **Проверить сквозной сценарий на итоговой версии:** запуск анализа → готовая карточка → вопрос → повторное открытие → реакция → следующий подбор. В PR отзывы и уточнения профиля ещё пишутся в консоль браузера, история обсуждений не реализована.
- **Не считать автовосстановление завершённым.** SqliteSaver подключён, но при старте сервера очередь переводит незавершённые задания в `interrupted` и предлагает отправить запрос заново; полноценный сценарий автоматического продолжения не подтверждён.
- **Перепроверить связку вопроса с заданием.** В PR `Service.ask()` читает `data/insights/<company>_<role>.json`, тогда как фоновые API-анализы сохраняются в `data/api/results/<run>/results.json`. Это требует проверки на карточке, полученной именно из API.
- **Подготовить данные для демонстрации.** Нужны локальные CSV кейса, ключ LLM, банковские материалы и нужные поисковые кеши. Попадание в кеш экономит квоту; новые запросы могут обращаться к модели. По умолчанию кеш банковского агента может использоваться даже при устаревших входах; для CLI есть `--analytics-strict-cache`.
- **Сверять документацию с кодом.** Описание PR местами отстаёт от его HEAD, а старые integration-reference документы описывают прежние ветки. Полный живой E2E в Docker автором проверен лишь частично.
