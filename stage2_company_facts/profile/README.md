# Профиль компании — выход этапа 2 для этапов 3–6

Один файл вместо чтения CSV на каждом этапе: `data/companies/profiles.jsonl`, одна строка на компанию.

```bash
python -X utf8 stage2_company_facts/profile/profile.py                       # 115 компаний с выручкой >= 15 млрд, ~6 с
python -X utf8 stage2_company_facts/profile/profile.py --ids U_42222 U_31505
```

| Поле | Что | Кто читает |
|---|---|---|
| `card` | поля `stage5 analyst_loop.profile.CompanyProfile`: ОКВЭД, регион, выручка, выручка группы, продукты, ФТС, доли платежей по разделам ОКВЭД | этап 5: `CompanyProfile(**p['card'])` — exposure и reasons считаются как раньше |
| `facts` | записи `deterministic_facts.build()` (`cat`, `text`, `depth`, `entities`) + `id` (`fact:<cat>_<n>`), `source` (таблица и поля), `kind` (`fact` / `hypothesis`) | этап 3 (генераторы читают `cat/text/entities`), этап 6 (ссылки на основания) |
| `scale` | класс `micro/small/medium/large` по 209-ФЗ (наибольшая из категорий по выручке и штату ФНС), основание класса, крупный бизнес по кейсу (>= 15 млрд) у компании и у группы, размер группы, перцентиль выручки среди всех / ОКВЭД / раздела ОКВЭД / региона | все этапы: разные инсайты лидеру и малому игроку |
| `data_quality` | флаги `common.data.DQ` | демо-фильтр, промпты |
| `search_terms` | виды деятельности, регионы, страны ФТС, виды деятельности группы — без дублей; `goods` / `inputs` — товары и сырьё отрасли простыми словами | этап 3, поиск |
| `links` | ключевые связи ([`links/links.py`](../links/links.py)): `suppliers` / `buyers` — топ-10 по сумме с долей, ОКВЭД, регионом, классом масштаба, «та же группа», «клиент Альфы» (контрагент вне таблицы — только id и сумма), концентрация top-1 / top-5 / HHI; `group` — размер, выручка, доля и место компании, главные виды деятельности, регионы, платежи внутри группы; `persons` — связи через общих физлиц вне своей группы | этап 3 (новости об отрасли контрагента), этапы 5–6 (риск зависимости: HHI ≥ 0.25 у поставщиков — 50 из 115 крупных) |
| `news_context` (с `--news`) | по 8 сильнейшим внешним факторам (без базовых и региона) — до 3 свежих новостей-подтверждений: id, заголовок, дата, источник, url, совпавшие ключевые фразы ([`news_context/context.py`](../news_context/context.py)). Новость принимается, если специфичная для фактора фраза есть в заголовке / начале текста и совпадение не одно слово; свежесть — полураспад 14 дней; один заголовок — одна новость. Ручная проверка на 4 компаниях: ~65 из ~70 новостей по делу; у факторов без подходящих новостей (страны ФТС без событий) — пусто, а не мусор | этапы 5–6 и UI: «почему важно сейчас» со ссылкой на первоисточник |
| `sensitivity` | чувствительность к 21 рычагу `A1–H1` (вес 0..1, `reasons`), см. [`sensitivity/`](../sensitivity/README.md) | сопоставление «новость × компания», этапы 4–6 |
| `external_factors` | внешние факторы: `topic` (каналы `exposure` этапа 5), `label`, `mechanism`, `keywords` для поиска новостей, `basis` (id фактов / поля `card`), `weight` 0..1, `rule` | этап 3 (запросы), этап 5 (связь с позицией банка по `topic`), этап 6 (объяснение «почему это важно») |

### Внешние факторы — [`external_factors/factors.py`](../external_factors/factors.py)
Детерминированно, без LLM. Вес: продукт банка (кредит/лизинг → ставка) 1.0; санкционная страна ФТС 0.9;
отрасль по классу/группе ОКВЭД 0.8, по разделу 0.6; страна ФТС, иностранный собственник 0.8; отрасль контрагентов
(доля платежей с известной отраслью ≥ 15%, другой раздел ОКВЭД) ≤ 0.6; регион 0.4; базовые (ставка, инфляция, налоги) 0.3.
Покрытие отраслевой базой клиентского сегмента (группа ≥ 15 млрд, `CLIENT`, 13,6 тыс.): класс/группа 18%, раздел 77%, нет 5%.
Тест: `python -X utf8 stage2_company_facts/external_factors/test_factors.py`.

Правила:
- выручка 1 000 ₽ — заглушка организаторов: в `card.revenue` будет `null`, класс считается по штату, перцентиль не считается;
- продукты в `card.products` — только у действующих клиентов (у бывших и потенциальных флаги могут быть прошлыми);
- перцентиль — доля компаний набора с выручкой не выше, наборы меньше 5 компаний не выводятся;
- доли отраслей в `card.pay_out` / `card.pay_in` считаются от **всех** исходящих / входящих платежей; `pay_out_total` / `pay_in_total` включают контрагентов с неизвестной отраслью. Поэтому сумма известных долей может быть меньше 1: остаток — нерасклассифицированные платежи;
- `check()` падает на дублях id, перцентилях вне (0, 100], долях платежей вне [0, 1] или с суммой больше 1 (с допуском на округление) и на «крупный по кейсу, но не large»;
- `load_profile()` при каждом вызове проверяет метаданные `profiles.jsonl`; после изменения, замены, создания или удаления файла следующий вызов использует его текущее состояние. Неизменённый файл не перечитывается, уже загруженный профиль текущего анализа не обновляется посередине;
- после обновления формулы долей ранее созданный `profiles.jsonl` нужно один раз пересобрать командой выше. Проверка версии файла не проверяет актуальность исходных CSV.

Офлайн-проверка долей и кеша на синтетических данных (без CSV и LLM):

```bash
python -X utf8 -m unittest stage2_company_facts.profile.test_profile
```

### Подключение к общему пайплайну

Адаптер `integration.py` загружает профиль один раз и отдаёт согласованные `card` и `facts` для одного анализа.
В `judge` используется `build([company_id], use_profiles=True)`: формат списка фактов остаётся прежним,
добавляются строки `profile_context` о масштабе, связях и правилах чувствительности. Последние явно помечены
как гипотезы. Стандартные генераторы новостей не используют эту дополнительную категорию.
Писателю передаются все факты, включая группу и платежи; в `loop` карточка и факты берутся из одного вызова адаптера.
Обычный `build(...)` без `use_profiles=True` по-прежнему строит факты непосредственно из CSV.

Такое подключение сохраняет общий интерфейс сборщика и не требует заменять генерацию текста, настройки моделей
или механизм поиска. Возможности v2/v3, потоки и снимок корпуса приходят из `mvp` при её объединении с этой веткой;
подготовка профиля сама по себе эти подсистемы не добавляет. Изменения банковских тезисов Вовчика интегрируются отдельно.

### Профиль как пояснение для агента

`context.py` оформляет выжимку `brief()` отдельным блоком «Пояснения из профиля компании»:

- в `judge` блок передаётся сразу в задаче и не обрезается лимитом 25 исходных фактов;
- в `loop` блок передаётся модели, объясняющей последствия, и автору инсайта без запроса дополнительных данных;
- автор и проверяющая модель получают пояснения отдельно от нумерованных исходных фактов. Номера остальных фактов
  сохраняются, строки пояснений не предлагаются как самостоятельные источники `fact:<n>`;
- веса 0..1 обозначены как эвристики, а факторы и чувствительности — как гипотезы для проверки. Нулевой вес или
  отсутствие канала в выжимке не является основанием автоматически отклонять новость;
- запрос фактов в `loop` не превращает пояснения в доказанные факты. Они не добавляются в `Dossier.facts()` / `refs()`
  и не меняют расчёты последствий, проверку достаточности данных или программный вердикт;
- поисковые алгоритмы и сопоставление каналов не меняются. Сохранённые веса Кирилла не подставляются в ранжирование v3.

При формировании конкретного промпта `compact_context()` убирает буквальные повторы масштаба и связей,
а также повторные проценты крупнейшего поставщика и топ-5, если оба значения совпадают с показанным фактом
концентрации исходящих платежей. Сам вывод о зависимости сохраняется. Ограничение первых 25 фактов учитывается:
скрытый факт не служит основанием сократить пояснение. Другие направления платежей, отличающиеся значения,
каналы чувствительности и механизмы не удаляются. Исходные факты и их номера не меняются; LLM для сокращения не вызывается.

Передаётся краткая выжимка: масштаб, до шести каналов, до шести внешних факторов и зависимость от поставщиков,
если её отмечает `brief()`. Это не передача всех полей JSON-профиля; дополнительные исходные факты доступны как раньше.
В `loop` поясняющая модель вызывается при достаточности оснований по существующим правилам, а автор — при положительном
вердикте: сам профиль не запускает дополнительные обращения к LLM.

Проверка маршрутов контекста с подменой моделей (без сети, CSV и запуска пайплайна):

```bash
python -X utf8 -m unittest stage2_company_facts.profile.test_profile stage2_company_facts.profile.test_context
```

### Совмещение с текущей `mvp`

Проверка файлов через `git merge-file` с локально доступной `origin/mvp` показала: `pipeline.py` объединяется
без конфликтов; новые пояснения пересекаются с обновлённым форматированием источников в двух местах.
При разрешении нужно сохранить обе доработки:

1. В `stage6_insight_generation/insight_writer/writer.py`, метод `Evidence.render()`: оставить из `mvp`
   оформление новостей через `article_context` / `render_untrusted`, оформление банковских источников и
   `UNTRUSTED_NOTE`. Для фактов использовать `facts = evidence_facts(self.facts)` и сохранить импорт помощника
   из `stage2_company_facts.profile.context`. Проверку цитат и число переписываний автора оставить из `mvp`.
2. В `stage5_insight_detection/analyst_loop/loop.py`, метод `BriefEvidence.render()`: после формирования списка
   `facts` сохранить добавление `d.profile_context`, а банковскую часть взять из `mvp`: `m.prompt_item()`,
   `bank_positions(d.bank)` и вывод выжимки позиции Банка. Изменения `article_context` также сохранить.

Это инструкции для будущего merge, сам merge этой доработкой не выполняется. Ветка `vladimir-all` отдельно
содержит прежние пересечения обработки ошибок и новых сценариев; отсутствие конфликтов всей интеграции не обещается.
