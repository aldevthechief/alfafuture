# Ретривер v3: ретривер v2 + генераторы от причин влияния (news-first)

Наследует v2 целиком (стандартные генераторы + фабрика на гибридном поиске e5 + qwen + BM25) и добавляет третий
источник кандидатов — **канальные генераторы**: новость оценивается по чек-листу «ключей влияния», компания — по
фактам, через которые она к этим каналам чувствительна (`experiments/news_channels`, чек-лист v2).

| Часть | Файл | Суть |
|---|---|---|
| Ключи влияния | `channels.py` | 30 пунктов под 20 родителями + «мусорка» X0 (хроника без последствий). Каждая новость получает перцентиль по каждому пункту от e5-large-instruct: запрос = инструкция + пункт + 3 примера-заголовка. Родитель = максимум по пунктам, событие = максимум по новостям. Векторы новостей — те же, что v2 уже кеширует; кодируются только 30 коротких запросов, новой модели нет |
| Фасеты компании | `channels.facets` | Без LLM, из фактов этапа 2: своя отрасль (13 каналов), отрасли сильных контрагентов (только если видимый поток ≥ 5% выручки), регион; атрибутные каналы — кредит или лизинг → деньги, иностранный владелец → собственность, ФТС → курс и санкции, штат > 250 → труд, концентрация покупателей → оборотный капитал, все → налоги и общие требования |
| Канальные генераторы | `channels.generators` | По генератору на фасет: событие ранжируется по `max перцентиль канала × близость к фасету` (близость — перцентиль гибридного поиска v2 по запросу фасета); атрибутные — по перцентилю канала |
| Пул и порядок | `candidates.py` | Пул v2 ∪ канальные события (квоты ∝ весу фасета, ≥ 200 событий). Порядок — приоритет v2 (`retrieval_v2.candidates.order`), каналам 20% веса, доли v2 пропорционально уменьшены |

Стоимость сверх v2: 0 ₽ и одна кодировка 30 запросов на корпус. Кеш фабрики v2 теперь проверяет весь вход (факты, бриф, промпты, модель, шаги, пул). Генераторы v3 видны в `generators` событий
(`source = 'channel'`, `reason` = фасет, `channel` = родители, `query` = факт компании).

## Сравнение с v2: топ-100 с полной разметкой судьёй v2 (22.10, 124 ₽)
Раньше у трёх из четырёх компаний половина топ-100 была не размечена, и разница между наборами частично зависела от
того, что случайно оказалось размечено. Поэтому судьёй размечены все недостающие события топ-100 четырёх наборов
(400 + 202 + 208 событий, ~0.31 ₽ за событие); в каждом наборе размечено 397–399 из 400. Полезно = потенциал, значимость
и механизм ≥ 2. Доля каналов в порядке 0.2.

| Топ-100 | U_106783 | U_150736 | U_212593 | U_9250 | Сумма |
|---|---|---|---|---|---|
| стандартные генераторы (без LLM) | 12 | 3 | 8 | 10 | 33 |
| стандартные + каналы (без LLM) | 20 | 3 | 20 | 18 | **61** |
| стандартные + фабрика (v2) | 21 | 10 | 18 | 19 | **68** |
| **v2 + каналы (v3)** | 25 | 10 | 22 | 22 | **79** |

- **v3 против v2: 68 → 79 (+16%)**, три компании из четырёх +3–4, четвёртая (U_150736, упаковка) без изменений. Топ-30: 23 → 25.
  Из 79 полезных v3 19 не нашёл v2; 8 из 68 полезных v2 ушли из топ-100 v3 (каналы вытеснили).
- **Каналы без LLM почти заменяют фабрику**: 61 против 68 (90%) при нуле ₽ и без кеша на компанию, а объединение
  полезных каналов и фабрики даёт 96. Но фабрика незаменима там, где мало фактов для фасетов: у упаковки (U_150736) каналы
  без фабрики дали 3 против 10, у неё нет кредитных продуктов, иностранного собственника и видимых платежей.
- **Предыдущий вывод «на отложенных компаниях выигрыша в порядке нет» был артефактом неполной разметки** и снят. Разделение
  на настроечные и отложенные компании больше не используется: долю 0.2 надо перепроверять на других компаниях с полной
  разметкой, она не варьировалась на полной разметке.
- Глубина пула (весь пул, неполная разметка): +12 полезных (93 → 105), +30% событий; в нём канальные события дают
  низкую точность.

Пул 4 компаний до исправления разметки (для справки, неполная разметка): настроечные v2 → v3 70 → 74, отложенные 23 → 31.

**Исправленная ошибка.** В первой версии v3 (6be5881) запрос фасета передавался строкой, и `HybridSearch` искал по
каждой букве отдельно: близость к отрасли компании была почти шумом, а цифры (93 → 103) относились к этой версии.
Теперь запрос — список из одной строки, тест это проверяет; цифры выше пересчитаны.

## Нейтральные примеры
Формулировки пунктов называют механизм, а не отрасль; 3 примера-заголовка каждого пункта — из разных отраслей и не из
отраслей оценочных компаний (упаковка, электрооборудование и сети, стройка, рестораны, маркетплейсы). Тест
`test_retrieval_v3.py` это проверяет. Замена на нейтральные примеры на метках ничего не изменила: полезных в пуле
столько же (46 / 26 / 12 / 19 в обеих версиях), то есть заметной подгонки под тестовые компании не было.

## Предрасчёт на Kaggle
`precompute.py push` собирает все запросы компаний (в кернел уходят только тексты запросов, id новостей и состав событий;
ни id компаний, ни фактов) и считает гибридный поиск v2 по всему пулу и 30 пунктов; `fetch` скачивает результат,
`load(news, events)` возвращает поиск `Frozen`, отвечающий из файла: генераторы, порядок и оценка идут на CPU за секунды.
Нужен для демо (индексация новостей заранее) и для оценок на многих компаниях: на локальной GTX 1650 расчёт 10 компаний
занимает десятки минут, на Kaggle 13 минут.

## Запуск
```bash
python -X utf8 stage3_news_search/retrieval_v3/candidates.py U_106783 --role cfo [--no-factory]
python -X utf8 stage3_news_search/retrieval_v3/test_retrieval_v3.py    # офлайн, без сети и данных
python -X utf8 stage3_news_search/retrieval_v3/eval_labels.py --labels <experiments/judge_v2/out>   # считает локально, медленно
python -X utf8 stage3_news_search/retrieval_v3/precompute.py push --companies U_… && … fetch
python -X utf8 stage3_news_search/retrieval_v3/eval_precomputed.py          # на готовых оценках, CPU
python -X utf8 pipeline.py U_106783 --role cfo --retrieval v3
```
По умолчанию `pipeline.py` пока на v2: v3 включается флагом `--retrieval v3`.

## Перед демо и на прод-стенде
Те же требования, что у v2 (новости индексируются заранее, энкодеры в памяти). Канальные оценки считаются из векторов
e5 на лету; если для демо-корпуса посчитать на Kaggle оценки ансамбля, их можно подложить так же, как векторы v2.

## Следующий шаг: каналы как «идея» для агента-инсайтера (не входит в этот PR)
Каналы нужны не только для поиска: они подсказывают агенту, **через какой механизм** событие может ударить по компании.
Всё нужное уже есть в выдаче ретривера: у события в `generators` записи `source = 'channel'` с родителями каналов
(`channel`) и фактом компании (`query`, начало — имя фасета). Предложение — передавать агенту до 3 строк-гипотез:
«классификатор заметил активность по каналу X (событие) и компания к нему чувствительна через факт Y: проверь, меняет
ли событие её деньги этим путём; если не подтверждается текстом новости и фактами — отметь». Подсказка — гипотеза,
а не утверждение; для событий, у которых главный пункт — «мусорка» (X0), подсказок нет.
- **Куда:** в слот «оценка этапа 4» промпта судьи (`stage5 insight_judge`, ключ `подсказки_классификатора`) без правки кода
  этапа 5; после теста — отдельный блок промпта и поле «какую подсказку подтвердил или отверг» для UI «почему важно».
- **Риск:** заякоривание (агент натягивает инсайт на подсказанный канал; для банка это риск навязывания продуктов).
- **Тест, ~100–300 ₽, нужно одобрение:** 40 событий × 4 компании, три варианта (без подсказок / настоящие / случайные
  каналы «плацебо»): доля инсайтов на полезных событиях, ложные инсайты на пустых (если с плацебо их больше — заякоривание),
  подхватывает ли агент настоящие подсказки чаще плацебо. Оставляем, если инсайтов не меньше, ложных не больше и
  плацебо подхватывается заметно реже настоящих. Связка пунктов с аналитикой банка (ставка → прогноз ставки, курс,
  сырьё, инвестиции) — там же. Подробный план: `experiments/news_channels/hints.md` в ветке `maxon`.

Не входит: фильтр «не экономика» по X0.
