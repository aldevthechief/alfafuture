# Этап 3. Ищем потенциально полезную новость

Задача — по фактам о компании и роли читателя **отсечь подавляющее большинство бесполезных новостей при высокой полноте**.
Оценка «интересно ли компании» — на этапе 4. Выход: shortlist 50–100 новостей на пару (компания, роль)
с объяснением, через какую грань компании пришла новость.

| Подход | Папка | Суть | Статус |
|---|---|---|---|
| A. Поиск по граням компании | [`facet_retrieval/`](facet_retrieval/candidates.py) | Компания → грани с весами: свой ОКВЭД 1.0, отрасли поставщиков и покупателей из платежей 0.7, страны ФТС 0.6, макроканалы из продуктов банка, раздела ОКВЭД и роли 0.5, группа и регион 0.4. `StemIndex` из `common/search.py`; оценка = max по граням `вес × cos`; квота на грань; штраф за криминал, аварии и общие СМИ | ✅ работает, индекс ~15 с |
| C. Генераторы кандидатов | [`candidate_generators/`](candidate_generators/generators.py) | Каждый генератор — одна причина «почему новость может стать инсайтом» из факта этапа 2 (своя отрасль, отрасли поставщиков и покупателей ≥5% потока, второй уровень цепочки, отрасли группы, продукты банка, макроканалы, страны ВЭД, регионы, гипотезы агента). Поиск гибридный: TF-IDF + энкодер FRIDA (`common/embed.py`), слияние рангов (RRF), опционально HyDE-заголовки. Работает на событиях (`events.parquet`). Бюджет [n, l] = [200, 800] событий делится по весам причин; генератор берёт от своего минимума до максимума, сверх минимума — только выше порога близости | ✅ офлайн-тест `test_generators.py` |
| D. Ретривер v2 (по умолчанию) | [`retrieval_v2/`](retrieval_v2/README.md) | Генераторы C + фабрика генераторов (агент GLM по профилю проверяет свои запросы на пуле и выбирает генераторы, кеш на компанию) на гибридном поиске e5-large-instruct + qwen3-emb-0.6b + BM25 по леммам; пул ~330–390 событий, порядок по приоритету. На метках судьи v2 (U_106783) в топ-30/100/200 — 8/21/31 из 74 полезных против 3/8/8 у C | ✅ офлайн-тест `test_retrieval_v2.py`, сравнение `eval_labels.py` |
| E. Ретривер v3 | [`retrieval_v3/`](retrieval_v3/README.md) | Ретривер v2 + канальные генераторы: новость оценивается по 30 «ключам влияния» (e5, те же векторы), компания — по фактам, через которые она к ним чувствительна; на метках судьи v2 (4 компании, топ-100 размечен полностью) 68 → 79 полезных (+16%); без фабрики и LLM каналы дают 61 против 33 у стандартных | ✅ офлайн-тест `test_retrieval_v3.py`, сравнение `eval_labels.py`; в `pipeline.py` — `--retrieval v3` |
| B'. HyDE | [`hyde_queries/`](hyde_queries/hyde.py) | `HydeQueryWriter`: на грань компании дешёвая LLM придумывает заголовки, которые повлияли бы на такой бизнес; они становятся запросами в A. Промпт `prompts/hyde.md`, кеш на грань | ✍ без запуска |

## Golden set — [`golden_set/`](golden_set/)
Реальных меток нет, поэтому используется синтетика.
- **`synthetic_needles.json` — «подсаженные новости»**: для каждой компании этапа 2 по две новости — `direct`
  (её отрасль) и `chain` (связь только через факт из таблиц), плюс «ловушки» с похожими словами без делового смысла.
  `eval_synthetic.py` подмешивает их в реальный корпус и меряет ранг.

  | Тип новости | recall@50 | recall@200 |
  |---|---|---|
  | Прямая | 89% | 100% |
  | По цепочке | 100% | 100% |

  Ловушки попадают в топ-50 у 4 из 9 компаний: их отсекает этап 4.
- **Смещение:** новости писались человеком, видевшим грани, поэтому оценка оптимистична.
- **Следующие шаги оценки:** слепая генерация «подсаженных новостей» LLM-ом по гипотезам этапа 2; полнота A относительно
  LLM-оценки этапа 4 на стратифицированной выборке (цель ≥95% при бюджете K); тест на специфичность (подмена компании → ранг падает).

```bash
python -X utf8 stage3_news_search/facet_retrieval/candidates.py U_68622 --top 30 --role cfo
python -X utf8 stage3_news_search/golden_set/eval_synthetic.py
```

Общий запуск `pipeline.py` использует ретривер v2 (D) по умолчанию в обоих режимах (`judge`/`loop`).
`--retrieval hybrid` включает генераторы C на FRIDA + TF-IDF, `--retrieval lexical` — поиск по граням. Адаптер `retrieval.py` превращает найденные события в строки
исходных новостей: `id` — ID новости-представителя, `event_id` — ID события, `event_news_ids` — все участники;
`sources`, `urls`, `generators` сохраняют источники и причины подбора. `--candidates` задаёт верхнюю границу числа событий.
Файл событий создаётся и актуализируется автоматически; ручной запуск кластеризации больше не обязателен.
