# Ретривер v2: стандартные генераторы + фабрика генераторов на гибридном поиске

Этап 3: по фактам компании отобрать события из пула новостей, которые могут стать инсайтом. Вход — факты этапа 2,
выход — события с причинами подбора (контракт `stage3_news_search/retrieval.py` в `mvp`).

| Часть | Файл | Суть |
|---|---|---|
| Гибридный поиск | `hybrid.py` | e5-large-instruct + qwen3-emb-0.6b (инструкция + запрос) + BM25 по леммам, слияние рангов (RRF); событие = лучшая его новость. Векторы новостей кешируются по хешу текста (`data/retrieval_v2/<model>.npz`): смена ID новостей их не сбрасывает, пересчитываются только новые тексты |
| Стандартные генераторы | `candidate_generators.generators` (без изменений) | по генератору на факт этапа 2 (своя отрасль, поставщики, покупатели, продукты банка, страны ВЭД, регион…), веса причин; квоты ∝ весу, ≥ 200 событий |
| Фабрика генераторов | `factory.py`, `prompts/` | агент GLM читает профиль, описывает бизнес-модель, проходит 24 канала влияния, проверяет свои запросы инструментом `probe` и выбирает пробы по номеру. Берём топ-13 событий каждого выбранного генератора. Результат кешируется на компанию (`data/retrieval_v2/factory/<id>.json`): на новом пуле новостей те же генераторы ранжируются заново без LLM |
| Пул и порядок | `candidates.py` | объединение (~330–390 событий); порядок — приоритет Σ вес/(1+ранг) по генераторам, нашедшим событие (фабрике 50% веса с 24.10, раньше 70%). Судье уходят `--candidates` (15) событий с квотой мест на каждый генератор ∝ его весу (`quota_pick`) |

Стоимость: фабрика ≈ 3.5–4.5 ₽ и ~7 минут на компанию один раз (7–10 вызовов GLM), дальше 0 ₽.
Без фабрики (`use_factory=False`) — только стандартные генераторы на новом поиске, без LLM.
Если агент не завершил работу, пул строится из стандартных генераторов (предупреждение в stderr).

## Сравнение со старым поиском (`eval_labels.py`, без вызовов LLM)
Метки — судья v2 (полезно = потенциал, значимость и механизм ≥ 2). «Старый» — то, что сейчас запускает
`pipeline.py --retrieval hybrid`: те же стандартные генераторы на TF-IDF + FRIDA, отбор n = l = K.

**U_106783** (735 размеченных событий из разных источников, 74 полезных; «ручные» — 28 событий, прочитанных человеком):

| Событий | Старый: полезных / ручных | v2: полезных / ручных | Неразмечено у старого |
|---|---|---|---|
| 30 | 3 / 1 | **8** / 1 | 4 |
| 100 | 8 / 5 | **21** / 11 | 23 |
| 200 | 8 / 9 | **31** / 16 | 79 |
| весь пул v2 (384) | — | **46** / 18 | — |

Даже если неразмеченные события старого поиска полезны с его же долей (~0.1), на 200 событиях это ~14 против 31.

**Ещё 3 компании** (упаковка, рестораны, стройка), полезных найдено из известных:

| Компания | Старый @30 / @200 | v2 @30 / @200 / весь пул |
|---|---|---|
| U_150736 | 0 / 2 из 10 | 4 / 9 / 9 из 10 |
| U_212593 | 0 / 2 из 16 | 3 / 13 / 14 из 16 |
| U_9250 | 1 / 6 из 27 | 2 / 15 / 24 из 27 |

Оговорки:
- У этих трёх компаний размечены в основном события фабрики и случайные: метки завышают v2, а у старого поиска
  неразмечено ~85–90% событий. Честное сравнение здесь — только на U_106783.
- Вклад частей на U_106783 (@100): новый поиск без фабрики — 11, с фабрикой — 21. Поиск даёт верх списка
  (@30: 3 → 7), фабрика — глубину.
- Вес фабрики 0.7 в порядке подобран на этих же 4 компаниях (варианты: лучший ранг 7 полезных в топ-30 суммарно,
  «фабрика первой» 18, вес 0.7 — 17): возможна подгонка.
- Векторы FRIDA для старого поиска взяты из прогона на Kaggle (первые 2000 символов текста вместо 1500).

## Запуск
```bash
python -X utf8 stage3_news_search/retrieval_v2/hybrid.py --seed experiments/retrieval/out   # векторы с Kaggle в кеш
python -X utf8 stage3_news_search/retrieval_v2/candidates.py U_106783 --role cfo [--no-factory]
python -X utf8 stage3_news_search/retrieval_v2/test_retrieval_v2.py    # офлайн, без сети и данных
python -X utf8 stage3_news_search/retrieval_v2/eval_labels.py          # сравнение на метках судьи v2
```
Без кеша первый прогон кодирует весь пул (~9k новостей × 2 модели) — на слабом GPU это долго (FRIDA на GTX 1650 —
~12 ч), поэтому векторы считаются на Kaggle (`experiments/retrieval/push.py`) и подкладываются через `--seed`.

## Перед демо и на прод-стенде
- **Новости индексируются заранее.** Когда пул новостей станет финальным, его векторы считаются на Kaggle и подкладываются
  через `--seed`. Векторы с Kaggle сейчас посчитаны на снимке корпуса от 20.10: после пересборки корпуса новым сборщиком
  тексты меняются, и нужен новый прогон.
- **Запросы генераторов кодируются в процессе, на каждый вызов.** Это ~70–100 запросов на компанию двумя энкодерами плюс
  ~10 с на сборку индекса BM25 (раз на процесс). На CPU это ~10–20 с, на ноутбучной GTX 1650 с троттлингом ~50 с.
  Чтобы демо не тормозило, процесс бэкенда держит энкодеры и индекс в памяти между запросами, а фабрика генераторов
  прогоняется для демо-компаний заранее.
- **Нужна нормальная машина:** ~+2 ГБ памяти к требованиям бэкенда на две модели (e5-large-instruct + qwen3-emb-0.6b)
  в fp16/bf16; в fp32 на CPU — ~4.5 ГБ.

Не входит (v3): скоринг новостей по 21 каналу ансамблем 5 моделей и канальный генератор (`experiments/news_channels`).
